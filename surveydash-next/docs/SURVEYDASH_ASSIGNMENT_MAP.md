# Surveyor assignment map

The user confirmed that respondents should be mapped by the sharing surveyor's task territory. Each stored response through a referral link contributes to that assignment's current province; this is not respondent residence, device/GPS coordinates or proof that fieldwork happened there. Changing a task's province moves its grouped response count without rewriting responses. Counts represent submissions, not verified unique individuals. Idempotent submission retries do not increment them.

Managers open **Surveyor → Peta**, or **Peta tim** from a survey's assignment panel. The selected survey scopes map figures and targets; all-survey mode sums responses and configured province targets across the visible workspace's surveys. Search, status and province selection filter the roster, without hiding historical responses on the map. Active surveyors are distinct usernames with active tasks; inactive tasks still contribute stored responses. Direct/imported submissions and assignments with no valid province are reported as unmapped rather than assigned an inferred location. In all-survey mode one surveyor can count in multiple provinces but only once in the overall active-person total.

Hover or keyboard focus immediately shows the province name, responses, active surveyors and target in a lightweight HTML tooltip. Selection shows persistent details for touch users. Native SVG focus rectangles are replaced with a province-shaped purple stroke, retaining a visible keyboard focus indicator. The map can color by responses or active surveyors. Target progress displays actual percentages above 100%, with a bounded visual bar and over-target amount. Short CSS transitions respect reduced motion. The native province selector and zoom/reset remain available. Browser interaction and visual behavior still require manual verification because browser access is blocked by the saved automatic approval policy.

**Atur target** saves a positive integer per survey/province, or clears it with an empty input. It is independent of the survey's overall target, never guessed or auto-distributed, and never closes a form or limits submission. The manager map and surveyor task portal refresh every 30 seconds while visible, with non-overlapping requests and cancellation on exit. Manager refreshes discard stale responses after a newer refresh or mutation. Surveyor cards show their own per-survey link total, with no cumulative response counter; revoked and unassigned surveys are excluded by server-side assignment/owner joins.

**Atur** on a team row and **Atur wilayah** within a survey open the same province dialog. Updates return the current scoped assignment list. The surveyor can read the assigned province on their own task but cannot edit it. Clearing a province removes only that setting. Changing/clearing a province does not rotate a referral token, activate a task, change response attribution or rewrite answers. Explicit deactivation/reactivation retains the province and follows existing token-rotation rules. Province information is not added to the public form, respondent submission or shared presentation.

## Storage and deployment

The additive `surveyor_assignment_regions` table references an existing assignment and stores `province_id`, the actual updating actor and timestamp. `survey_province_targets` has a survey/province composite key, integer target (1–10,000,000), updating actor and timestamp. Existing assignment/profile/response tables and their positional inserts are unchanged. The manager assignment PATCH retains the strict active-state or province alternative. The separate owner/manager/origin-guarded `/api/surveys/[id]/province-targets` endpoint accepts only `{ provinceId, target: number | null }`; extra keys, invalid/zero/fractional targets and cross-owner requests are rejected. These settings never enter anonymous forms or public responses.

PostgreSQL requires the idempotent tables from `src/lib/db.ts` before releasing code that queries them; `initializeDatabase` includes them for setup. Each rollout backs up the intended cloud database first and applies only the missing additive table. SQLite creates it with its existing schema initialization. Cloud backup discovers all tables automatically, and staging restore includes both settings tables after their parent records. Previous code remains compatible with the additive schema. Runtime map requests perform no DDL or external geography requests.

## Geometry and attribution

The static SVG geometry is generated from [denyherianto's 38-province dataset](https://github.com/denyherianto/indonesia-geojson-topojson-maps-with-38-provinces/tree/80aa4a90ac7eef5136eaa2b551b6aa5d198be27d), pinned to commit `80aa4a90ac7eef5136eaa2b551b6aa5d198be27d`. Data is licensed CC BY 4.0, independently of the repo's MIT code license. Visible credit links to the source and [local license/change notice](/licenses/indonesia-provinces.txt). `scripts/build-province-map.mjs` downloads only JSON/license text, validates all 38 provinces and coordinate bounds, projects rings to a near-equatorial display plane and rounds projected coordinates. IDs are internal name slugs, not official administrative codes. All six Papua-region provinces are represented; detailed district boundaries are outside this version.

The derived geometry is about 40 KB and the map component is loaded on demand. No map library, tile service, API key or new image asset is added. A geography-only PNG render was inspected for the island/province outline; it is not browser/UI verification. Browser map interaction, real keyboard/pointer operation, zoom, mobile layout and visual QA remain unverified because the saved automatic browser approval policy denies access.

The small province-name catalog is a JSON data file separate from geometry. The shared helper derives canonical slugs from it, so assignment controls load only names while the map loads paths on demand. Map shapes carry those IDs and use the same catalog for labels. This avoids repeated executable object literals and prevents name catalogs from drifting between the map and controls. Team filters and empty-list captions are separate helpers to keep the stateful manager component readable.

## Framework patch

The first build surfaced npm security advisories for installed Next.js 16.4.0: [Server Actions denial of service](https://github.com/advisories/GHSA-p3m5-59mp-jv5r), [SVG image optimization](https://github.com/advisories/GHSA-2464-fhr4-w9xw) and [`use cache` typed arrays](https://github.com/advisories/GHSA-673q-mjm6-r5xr). npm reports the affected range through 16.4.0. Next.js and eslint-config-next are pinned to the compatible 16.4.2 patch; React and application APIs are unchanged. Final validation is repeated on that version before release.

## Validation

On Next.js 16.4.2, all 100 tests, strict ESLint, TypeScript and the optimized production build passed. Tests cover target isolation/upsert/clear, values above 100%, inactive-task response conservation, idempotent retries, separate per-survey personal counts, inaccessible unassigned surveys, and tooltip position bounds. npm's bulk advisory endpoint returned no Next.js advisories for 16.4.2 at the original patch verification. Existing conservative ESLint peer ranges in eslint-plugin-import/jsx-a11y/react still warn about the already-installed ESLint 10; these same plugin versions/ranges predate this change and strict lint passes.

A fresh isolated local production server passed 106 HTTP checks covering manager/surveyor/anonymous role guards, target owner/origin/strict-input rejection, saved/cleared targets, above-target anonymous responses, retry deduplication, separate personal totals per survey, unassigned/foreign survey exclusion, inactive-task history, unchanged referral links, a 38-province SSR map, unmapped direct responses, license/CSS delivery, guide persistence and existing artwork/motion delivery. Respondent forms contain no assignment province or private targets. PostgreSQL staging exercised both settings tables and above-target response submission inside a rolled-back transaction, with no synthetic data retained. The additive staging migration preserved all existing survey, submission and assignment counts. Browser visual/interaction limitations remain as stated above.
